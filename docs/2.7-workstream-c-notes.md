# AnchorDesk 2.7 Workstream C notes

## Requester identity and authorization

The portal principal is an existing `Contact`, not a staff `User` with a new
role. A resolved requester is a discriminated principal containing the
contact's id, current company id, name, and email. It never has a `UserRole`,
never populates `request.user`, and cannot be used to mint staff API/MCP
credentials.

Portal and staff logins share the server-side `Session` table, but every row has
an explicit `staff` or `portal` scope and exactly one matching principal foreign
key. Both the resolver and a boot-verified PostgreSQL constraint enforce that
pairing. Portal sessions use the existing opaque HttpOnly cookie mechanism and
expire after 24 hours. A portal cookie is accepted only for an explicit
method-and-path allowlist; it is rejected before any staff, MCP, OAuth, device,
or administrative handler can run.

Contact email is not unique in the existing CRM model. Login therefore performs
a case-insensitive lookup capped at two matches and fails closed unless exactly
one contact owns the address. Guessing between duplicate contacts would turn an
ordinary CRM data-quality problem into an authorization decision. The generic
login response does not reveal that an address is missing or ambiguous.

Every ticket read is constrained in the database by both `contactId` and the
requester's current `companyId`. The redundant company predicate is deliberate:
it also fails closed if a ticket/contact association is corrupt or was changed
incompletely. Foreign and missing records are both reported as unavailable.
Company, contact, source defaults, status, and priority on creation are all
server-owned.

Changing a Contact's normalized email or company revokes all of that Contact's
portal sessions and outstanding links in the same transaction as the identity
edit. Link issuance takes a compatible row lock and rechecks the expected email
and company, so an old mailbox cannot race a Contact reassignment and inherit
the new company's boundary.

Contact identity writes and link issue/redemption share a transaction-scoped
advisory lock. That closes the duplicate-email phantom race that a lock on only
the selected Contact cannot prevent. Creating or editing a Contact into an
ambiguous normalized address revokes the portal links and sessions of every
matching Contact; portal authentication remains unavailable until staff repairs
the CRM data.

Merged survivors are hidden from the portal in v1. AnchorDesk permits warned
cross-contact and cross-company staff merges, and attachments do not retain
enough per-item origin/audience data to prove that the resulting conversation
belongs to one requester. Hiding those records is a rough product edge; showing
them would be a potential breach.

The same reasoning applies when staff reassign a ticket's Contact or company:
ownership of the row does not prove ownership of its prior conversation. The
update permanently quarantines that ticket from v1 portal access. Restoring it
requires a future reviewed-transfer flow or artifact-level audience ledger; a
second reassignment cannot silently clear the quarantine.

## Magic-link threat model

### Token guessing and database disclosure

Each link contains an independently random 128-bit selector and 256-bit
verifier. Only SHA-256 hashes of both parts are stored. The selector permits an
indexed candidate lookup without storing usable bearer material; the verifier
is compared as a fixed-length digest with a timing-safe comparison. A database
read therefore does not yield a login credential, and offline guessing remains
bounded by 256 bits of entropy.

An indexed hit and miss are not assumed to have identical database timing.
Malformed and unknown selectors still perform the lookup and a fixed-length
dummy-digest comparison, and the random 128-bit selector space is not remotely
enumerable enough for that distinction to become a practical oracle.

### Replay, races, expiry, and mail scanners

A verifier is accepted only when a conditional database update can change that
row from unused to used while it is still unexpired. Concurrent redemptions can
therefore produce at most one portal session. Links expire after 15 minutes and
spent/expired rows are pruned.

Requesting a newer link does not revoke an older unspent link. Revocation would
let anyone who knows a Contact's address repeatedly invalidate the requester's
mail before it can be opened. Each issued link instead keeps its own short
expiry and one-use boundary, while the per-recipient limiter bounds how many can
be minted.

The raw token is placed in the URL fragment of
`/portal/login#token=...`, not in a query string and not on a consuming GET
endpoint. Fragments are not sent in HTTP requests or Referer headers. The portal
removes the fragment from browser history before exchanging it in a JSON POST.
This also prevents common email security scanners from consuming a one-time
link merely by following it.

Links are built from the configured `APP_BASE_URL`, never the request's `Host`
or forwarding headers, so a spoofed login request cannot redirect the bearer
secret to an attacker-controlled origin.

Consumption and server-side session creation commit in one transaction. A
failure rolls both back, so no session can escape without consuming the link
and no committed consumption can lose its session. The token remains eligible
only until the original short expiry; a concurrent successful redemption still
wins the conditional update and makes every retry fail.

### Timing and email enumeration

Known, unknown, duplicate, malformed, and temporarily undeliverable addresses
receive the same `202` status and the same generic body. Link issue/delivery is
decoupled from the response, so database and SMTP latency are not exposed as an
account-existence oracle. Logs do not contain the submitted email, raw token,
or provider error text that could echo the recipient.

Dispatch is deliberately best-effort after the `202`; a process crash before
the asynchronous task runs can drop that request. The generic response therefore
promises neither account existence nor delivery, and the requester can safely
request another link.

The request endpoint is rate-limited by a SHA-256-derived per-recipient key with
the already-installed Fastify limiter. Verification is separately throttled per
presented token even though a 256-bit verifier is not realistically
brute-forceable. Target-based keys are deliberate: the shipped nginx topology
otherwise makes every requester appear to have the proxy's socket address and
lets five requests deny login to every customer. Keys contain neither submitted
emails nor raw tokens. The current limiter is in-process; a multi-replica
deployment needs a shared limiter such as Redis.

### Session theft, CSRF, and email-account compromise

Portal sessions remain opaque, hashed-at-rest, HttpOnly, SameSite cookies and
are marked Secure on HTTPS deployments. SameSite protects portal mutations from
ordinary cross-site form posts; no bearer token is kept in browser storage.
Logout revokes the server-side row immediately.

Magic-link authentication necessarily trusts control of the contact's mailbox.
It cannot protect against a compromised mailbox or a malicious mail forwarder.
Short expiry, single use, fragment transport, and the shorter portal session
limit reduce that exposure without pretending to eliminate it.

Token redemption requires `application/json`. A cross-origin HTML form can send
urlencoded data and cause a response to set cookies even when SameSite prevents
it from sending an existing cookie; without the media-type check, an attacker
could swap the victim into the attacker's requester session. JSON forces a CORS
preflight, and AnchorDesk does not grant cross-origin portal access.
The link-request endpoint has the same media-type requirement, preventing
cross-site form submissions from using the portal as an unsolicited-mail
trigger.

## Serialization and attachment boundary

Portal DTOs are constructed from explicit object-literal allowlists. They do not
spread Prisma records. Ticket company/contact details, assignee and team
identity, custom fields, SLA internals, external/sync fields, hierarchy and
merge state, labels, checklists, audit history, devices, and script jobs are not
part of the contract.

Notes carry explicit `public`/`internal` visibility and a separate provenance
(`via: portal` for requester comments). This was necessary because existing RMM
script output also used `noteType: note`; treating every ordinary note as public
would leak script logs. Portal replies expose only allowlisted content,
sanitized HTML, mail direction, timestamp, id, and the derived labels `You` or
`Support`—not the raw provenance, staff identities, or mail addressing headers.

Portal comments enter the ordinary note/event path and are marked for the
existing outbound ticket-sync path. The route then attempts the same provider
push best-effort; local persistence and its audit record remain authoritative
if a provider push fails.

External-provider comments are internal unless their adapter supplies positive
requester-audience evidence. ConnectWise exposes only an explicit external
detail note; missing/contradictory/internal-analysis flags fail closed. The
current Jira platform adapter cannot prove Jira Service Management's public
comment bit, so Jira comments remain staff-only in v1 rather than guessing.

Attachments have an explicit portal-visible classification. Downloads use a
portal-specific route that rechecks contact, company, ticket, merge, and
visibility scope before reading storage. DTOs never expose storage backend,
object key, or creator identity.

Requester uploads are limited to 50 MiB total per request in addition to the
existing 25 MiB-per-file/10-file parser limits, and upload requests are
throttled per Contact. Storage bytes are staged and removed if the
ownership-checked metadata/audit transaction does not commit.

Pre-2.7 email notes had no audience field even though email was the historical
public-correspondence representation. An idempotent startup migration marks
only unclassified (`via IS NULL`) email notes and their linked attachments as
public. Runtime portal queries and the serializer then check only the explicit
visibility flags. In particular, an email-typed row explicitly classified
internal remains private.

## Deliberately omitted from v1

- Passwords, passkeys, MFA, and social/enterprise SSO for requesters.
- Company-wide ticket visibility and delegated requester administrators.
- Editing ticket fields, closing/reopening tickets, editing/deleting comments,
  and deleting attachments.
- Requester notification preferences and a portal-specific notification feed.
- Portal access to merged conversations until artifact-level audience
  provenance exists.
- Portal access after ticket ownership transfer until a reviewed transfer flow
  exists.
- Jira/JSM inbound comments until the adapter obtains an explicit public bit.
- A knowledge-base article reader. Workstream C consumes only the supplied
  search contract.
- A shared/distributed auth rate-limit store.
- A durable SMTP outbox/recovery ledger. SMTP delivery and database persistence
  cannot be one transaction; a relay success followed by a database failure can
  still require operator reconciliation.
- Parallel staff and requester sessions in one browser profile; the single
  session cookie represents one principal at a time.

## Spec issues and judgement calls

The search contract returns article slugs but does not define the route or API
for reading an article. The deflection panel can truthfully show search results,
but Workstream D must own the reader/link contract; Workstream C does not invent
one.

The portal scope did not discuss merge audience changes. Because existing merge
rules deliberately allow acknowledged cross-company moves, an ownership check
on only the surviving ticket is insufficient. V1 hides all live merge targets
rather than guessing which moved notes and files remain safe.

The original model also did not distinguish public attachments and used
`noteType: note` for both customer comments and RMM output. The implementation
adds explicit visibility instead of encoding security in those historical
conventions.

Finally, older IMAP-created tickets did not consistently carry `contactId`.
Company-domain inference alone is not enough for an “own tickets” portal.
Inbound mail can associate a sender only when exactly one Contact matches; an
ambiguous sender remains company-linked but portal-invisible.
