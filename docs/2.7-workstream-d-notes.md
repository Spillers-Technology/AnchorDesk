# AnchorDesk 2.7 Workstream D — Knowledge Base

## Decisions

### Stable slugs and collisions

An article gets its slug once, when it is created. The base is derived from the
title by Unicode normalization, lower-casing, and replacing non-URL characters
with hyphens. Collisions use deterministic numeric suffixes (`printer-setup`,
`printer-setup-2`, and so on). The database unique constraint is the concurrency
arbiter; a create that races on the same slug retries with the next suffix.

Title edits never update the slug. Deletion is a soft delete that unpublishes the
article but keeps its row and unique slug. This deliberately reserves retired
URLs: an old link returns 404 instead of ever resolving to unrelated new
content. V1 does not add redirects or aliases because there is no slug rename
operation.

`author` is a byline snapshot rather than a foreign key. This follows the
existing actor identity used by auditing, remains meaningful if a staff account
is renamed or removed, and works for both REST and MCP mutations.

### Visibility is safe by construction

Portal search and portal article reads have dedicated repository functions:
`searchPublishedPortal(query, limit)` and
`getPublishedPortalBySlug(slug)`. Neither accepts a visibility or publication
option. Both hard-code `deletedAt = null`, `published = true`, and
`visibility = portal`, then check the same postcondition before serialization.
The portal search route also sends staff callers through this restricted path
whenever they explicitly request `visibility=portal`.

This keeps authorization and content visibility as separate defenses. A later
portal-authentication mistake cannot turn the portal repository call into an
internal or draft query. Tests cover internal, draft, deleted, and deliberately
misbehaving mocked-result cases.

### Portal authorization integration seam

Workstream C's portal principal is not present on this branch. The single seam
is `authorizePortalKbRead()` in
`backend/src/middleware/kbPortalAccess.ts`. At present it allows only these
exact, read-only public shapes:

- `GET /kb/search?...&visibility=portal`
- `GET /kb/portal/:slug`

Published portal articles are therefore anonymously readable in this worktree,
with per-route rate limits. When the Contact-backed portal session lands,
Workstream C should replace the marked `return true` in that function with its
session check. It should not move or duplicate visibility logic there; the
repository boundary remains the authoritative content constraint.

The required search response is implemented exactly as
`{ items: [{ id, slug, title, excerpt, score }] }`, ordered by descending
relevance. `/kb/portal/:slug` is an additional full-article read needed by the
eventual portal UI.

### Authoring boundary

Administrators and technicians can create, edit, publish, and delete articles;
read-only staff can browse published articles. Technicians are intentionally
authors because they are closest to the repeated answers this feature is meant
to capture. REST and MCP use the same boundary. Every mutation records its audit
entry in the same transaction as the article change. Body edits put compact
before/after lengths and SHA-256 hashes in the audit record rather than copying
up to two megabytes of HTML into the audit log.

The existing admin rail is itself administrator-only, so the admin panel is
available there for administrators while technicians get the same management
controls in the normal Knowledge Base view. This preserves the application's
existing admin-navigation RBAC instead of making the admin shell partly
technician-accessible.

### HTML and search

All article HTML goes through the existing mail sanitizer on write. Plain search
text is derived from that sanitized HTML, and returned article HTML is sanitized
again before serialization. The web reader uses the existing `HtmlContent`
component used by ticket content, which applies DOMPurify at render time.

Search uses the existing PostgreSQL stack: weighted English FTS for title,
category, and body plus `pg_trgm` similarity and literal substring fallback.
The matching optional GIN indexes are installed through `pgExtras.ts`. Excerpts
come from sanitized plain text and prefer a short window around the matched
phrase or token. Browse/list responses are body-free summaries; their query
selects at most 221 plain-text characters per row, and the full sanitized body
is fetched only when an article is opened.

The shared renderer now wraps sanitized tables in a keyboard-focusable,
horizontally scrolling region. Code blocks scroll internally and images shrink
to their container. The mobile capture checks both sides of the requirement:
the document must not be wider than the viewport, and the deliberately wide
fixture table must have real internal overflow rather than clipped columns.

## Deliberately left out of v1

- The customer portal UI and Contact-backed portal session implementation.
- Managed KB image uploads or attachments. Remote/data images are still subject
  to the shared sanitizer policy.
- Revision history, review/approval workflows, scheduled publication, and
  rollback.
- Category taxonomy administration; category is free text in v1.
- Slug redirects/aliases, usage analytics, article feedback, and direct
  insertion into the ticket composer.

## Spec judgments

The request simultaneously asks for technician authoring and an admin-panel
entry. AnchorDesk's established admin rail is administrator-only, so exposing
that shell to technicians would have weakened an unrelated RBAC boundary. The
normal tech-facing KB view therefore includes authoring controls, while the
admin panel is an administrator convenience wrapper around the same view.

The spec calls the slug stable but does not define deletion reuse. Reusing a
deleted slug could make a saved public URL silently point to different content,
so deleted rows retain and reserve their slug.

Until Workstream C is merged, treating published `portal` articles as public is
more coherent than inventing a temporary staff-shaped portal principal. The
authorization decision is isolated and clearly marked for replacement, while
the data boundary is already final.

## Verification

The following checks pass in this worktree:

- `cd backend && npx prisma validate`
- `cd backend && npm test` — 62 suites passed; the opt-in live PostgreSQL suite
  is skipped by the default unit-test command.
- `cd backend && npm run build`
- `cd web-client && npm test`
- `cd web-client && npm run lint`
- `cd web-client && npm run build`
- Syntax checks for both mobile capture scripts.

The Playwright mobile capture matrix was not executed in this session because
neither `playwright` nor `playwright-core` is installed in the worktree. The KB
list, reader, editor, and `?admin=knowledge-base` captures are registered, and
the reader capture includes runtime assertions for document width and internal
table scrolling.

The live test is available as `cd backend && npm run test:kb-postgres`. It
creates realistic portal, internal, and draft articles, installs/checks the FTS
and trigram indexes, verifies ranking and the portal boundary against PostgreSQL,
and cleans up its fixtures.

Docker Desktop could not be used from this managed Windows session: the service
is stopped, this account cannot start it, and the Docker named pipe returns
permission denied. The live test therefore stops with Prisma `P1001` at
`localhost:5432`. This is an environmental verification remainder, not reported
as a passing check. The runner also refuses non-local database URLs by default
so this fixture-writing proof is not accidentally pointed at production. Once
Docker is available, run `docker compose up -d db`, `npx prisma db push` from
`backend/`, then `npm run test:kb-postgres`.

One operational issue predates this workstream: Fastify is not configured to
trust the nginx proxy, so in the packaged deployment its in-process rate-limit
keys may see nginx's container address rather than the end-client address. The
new anonymous KB limits therefore fail conservatively (shared quota, not a
visibility bypass), but deployment should eventually use a narrowly trusted
proxy configuration or enforce those limits at nginx.
